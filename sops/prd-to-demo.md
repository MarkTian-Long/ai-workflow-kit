# 从需求说明到可评审的本地 Demo

用于已有需求基线、准备制作或修改交互式 HTML Demo 的任务。目标是让评审者看见约定的用户行为，同时知道哪些能力只是模拟。纯静态视觉稿可只检查相关部分。

## 开始前

先定位当前有效的需求文档、已确认决定和 Demo 源文件，约定本轮用户、场景、范围及交付位置。历史聊天只帮助找来源；需求互相冲突时，先澄清会改变结果的决定，不通过修改措辞掩盖冲突。

选一条用户旅程，说明输入是什么、对象之间如何关联、谁可操作、成功会看到什么，以及失败时如何继续。标明真实接口、固定样例、临时本地状态和未实现能力。没有后端的页面不能承诺持久保存、权限隔离或真实发送。

## 制作与检查

1. **按行为对照。** 给每个重要行为找到需求依据、界面入口、结果状态和一条可执行检查。例如“换一个输入后，旧结果应失效”，需要同时检查结果区、标题、统计和导出内容。
2. **实现完整的模拟过程。** 成功、等待、无结果、输入不足和失败分别表达；不能用同一个空页面代表所有情况。尚未实现的动作应明确说明限制，不能弹出虚假的成功提示。样例数据与实际测量结果分开标记。
3. **检查信息是否够用。** 让未参与设计的人从页面判断该做什么、输入是否合格、结果依据是什么、下一步能做什么。设计解释放在评审材料；影响操作的限制留在界面。
4. **做静态预检。** 检查脚本语法、必要资源、旧字段、未授权数据及意外外部请求。若要求自包含，断开非必要外网资源仍应能完成约定旅程。
5. **实际打开浏览器操作。** 在约定访问方式和视窗中点击关键路径，检查可见结果。至少覆盖一条成功旅程、一个无效输入、一个失败或无结果状态，以及输入变更后旧结果的处理。存在角色限制、筛选、人工操作、报告或重置时，检查相应影响；直接调用函数不能替代界面操作。
6. **找一个能推翻实现的例子。** 例如删除当前输入后旧报告仍可导出，或模拟权限不足时仍提示操作成功。修复后只重跑受影响路径及已发现的失败路径。默认验证实际桌面场景；明确有移动端用途或已发现布局问题时再增加窄屏检查。

## 变更与交付

需求或输入关系改变时，先确定影响范围，再同步更新需求正文、Demo、受影响流程图、截图和使用说明。不要只更新一个展示形式，留下另一个继续表达旧规则。新的行为未经确认，不因为页面做出来就自动成为需求。

交付说明只需回答：使用哪份需求、可操作什么、完成了哪些浏览器检查、仍有什么限制。必要截图和检查记录留在任务已有位置；涉及私人或业务材料时遵守原来的保存与分享范围。

完成约定旅程、已发现问题修复并验证后即可交付。本地 Mock 的检查结果只支持该版本的模拟交互，不证明真实模型效果、接口能力、生产权限、性能或客户验收。

## 可复制的任务请求

> 请以【当前需求文档】和【已确认决定】为基线，创建或修改【Demo源文件】，供【使用者】完成【核心旅程】。本轮只包含【范围】，采用【合成数据/获准样例】；【未实现能力】须在行为与文案中说明。先建立必要的行为对照，再实现并通过实际浏览器点击检查成功、异常和输入变更路径。若改变需求或流程，同时更新受影响正文、图示和说明。请交付可用入口、实际验证结果和剩余限制；本地模拟不作为生产或客户验收证明。
